*Structured data management in Emacs using SQL*

~tabularium~ provides a scalable data entry and management system within Emacs, using SQLite as its primary backend.  It is designed to be an accessible user interface for datasets with thousands of entries and dozens of columns, in which standard Emacs tools begin to exhibit performance limitations.

* Design and Scope

~tabularium~ creates a data management ecosystem within Emacs centered around paired database/schema files, tracked via a central registry.  Databases are stored within standard SQL database files, and corresponding schema files provide the structure of these databases in Elisp.  Interaction with the database is handled via built-in Emacs tools, including ~tabulated-list-mode~ for row/column display, ~forms-mode~ for data viewing/entry, and ~sqlite.el~ for the database backend.  The result is something close in spirit to Microsoft Access or LibreOffice Base, but fully integrated into Emacs—leveraging Emacs's standard completion frameworks, keyboard-driven navigation, and version control support.  Several useful elements from common spreadsheet software such as Microsoft Excel and LibreOffice Calc are also implemented for ease-of-use.  An EIEIO-based backend abstraction layer adds optional support for PostgreSQL (via ~emacsql-pg~) and leaves room for future extension to other database systems.

This package was developed out of a need to more adeptly handle large datasets within Emacs.  Emacs's built-in tools such as ~org-table~ and ~csv-mode~ handle human-readable tables and flat files well, but neither scales gracefully to thousands of records with rich schemata, field-level completion, or computed fields.  Conversely, packages like ~emacsql~ provide raw database access but lack a data management interface, and ~esqlite~ offers SQLite bindings without a user-facing layer.  ~tabularium~ is designed to occupy the space between these tools and full external database applications.

* Features

- *SQL-backed storage* — SQLite by default, with an extensible backend architecture
- *Schema-driven data structure* — field types, defaults, choices, validation, and computed fields
- *Multiple entry modes* — form-based (with per-field completion), minibuffer prompts, and quick entry for high-volume workflows
- *Rich querying* — filter, search, count, and aggregate across any field type; fuzzy find via ~completing-read~
- *Spreadsheet operations* — undo/redo, copy/paste, dired-style marking, multi-column sort, freeze rows, fill, query-replace, column clipboard, and reindexing
- *Completion system* — historical (frequency-ranked), recent, vocabulary (file or inline), related (contextual co-occurrence), filtered (~SQL WHERE~), custom function, and union sources
- *Saved views* — named presets for filter, sort, and column configuration
- *Import/export* — CSV, TSV, and org-table import; CSV/TSV export (RFC 4180-compliant)
- *Hydra and Transient menus* — discoverable command interface
- *Version control-friendly* — designed for Git and Syncthing workflows

Default keybindings for all modes are documented in [[file:KEYBINDINGS.org][KEYBINDINGS.org]].

* Installation

~tabularium~ is not yet available in any Emacs package repository.

** With ~elpaca~ or ~straight~

Install directly from the online repository using ~elpaca~ or ~straight~:

#+begin_src emacs-lisp
(use-package tabularium
  :ensure (:host codeberg :repo "phmcc/tabularium")
  :config
  (require 'tabularium-menu))
#+end_src

** Manual

Alternatively, clone the repository and put the package in the Emacs load path:

#+begin_src emacs-lisp
(add-to-list 'load-path "~/path/to/tabularium")
(require 'tabularium)
(require 'tabularium-menu)
#+end_src

* Quick Start

** 1. Create a database

#+begin_example
M-x tabularium-create-database RET expenses RET ~/Documents/expenses.db RET
#+end_example

This creates two paired files: =expenses.db= (the SQLite database) and =expenses.schema.el= (the schema definition).  An interactive wizard prompts for field definitions.

Three alternate creation paths are available for non-interactive workflows:

- ~tabularium-create-database-quick~ takes a one-line spec string of the form =id:type:flag id:type:flag…= (types: ~text~, ~integer~, ~number~, ~date~, ~time~, ~datetime~, ~choice~, ~boolean~; flags: ~required~, ~primary~/~pk~, ~long~, or a ~|~-separated list of choices).
- ~tabularium-create-database-from-header~ creates a text-only schema from a pasted tab/pipe/comma-separated header row.
- ~tabularium-create-database-from-schema-file~ uses an existing =.schema.el= as a template for a new database — like \"Save As\" for schemas.  Prompts for a new name and new database file, then writes a fresh schema mirroring the source's fields, saved views, highlight rules, default sort, and backend choice, but pointing at the new database file (which starts empty).

All four variants are also accessible from the menu under =C= (sub-keys =C=, =Q=, =H=, =S=).

** 2. Edit the schema (optional)

The wizard produces a working schema, but the generated =.schema.el= file can be refined further—for instance, to add completion sources, views, or quick-entry fields.  See "Schema Files" below for the full specification.

** 3. Open and use

#+begin_example
M-x tabularium-open RET expenses RET
M-x tabularium-view RET
#+end_example

From the view buffer, entries can be created, edited, sorted, filtered, marked, and exported.  Form-based entry provides per-field completion; quick entry prompts only for selected fields.

| Command                        | Description                                                     |
|--------------------------------+-----------------------------------------------------------------|

~tabularium-view-filter~ (bound ~f f~) is a single entry point that prompts for the filter type — substring, exact, or numeric — and runs the matching command, parallel to the ~h a~ highlight dispatcher; the substring filter is also directly available as ~f s~.  Filters are progressive *layers*: the first call sets a base layer, and each subsequent call prompts for a logical connective (AND, OR, AND NOT, OR NOT) so the stack reads as a boolean expression.  The modeline shows it compactly — ~(genre = Fiction) ∧ (price > 20)~ — eliding the middle when more than three layers are active.  ~tabularium-view-filter-buffer~ (bound ~f l~) opens the *Filter Rules List* buffer: an interactive list of every layer numbered in evaluation order, with the connective in its own column.  From it, ~m~/~u~/~U~/~t~ mark and unmark layers, ~x~ removes the marked ones, ~c~ cycles the connective of the layer at point, ~RET~ modifies a layer, and ~M-p~/~M-n~ move a layer up or down — a roomier counterpart to the single-line modeline summary, parallel to the Highlight Rules List buffer.

* Entry Mode (~tabularium-entry-mode~)

Entry mode provides a form-based interface for creating and editing individual records.  Each field is displayed on its own line with its prompt label, and completion is available where configured in the schema.

Three entry methods are available:

- *Form entry* — opens a dedicated buffer with all fields laid out vertically; best for complex schemas and careful data entry.
- *Prompt entry* — prompts for each field sequentially in the minibuffer; suitable for quick keyboard-driven entry.
- *Quick entry* — prompts only for fields listed in ~:quick-entry-fields~; ideal for high-volume entry with consistent defaults.

The ~tabularium-entry-method~ variable controls the default method; a prefix argument before any entry command invokes the alternative.

* Registry Mode (~tabularium-registry-mode~)

The registry tracks all known databases.  ~M-x tabularium-registry~ displays a listing with each database's name, schema status, and file path.  From this buffer, databases can be opened, viewed, created, registered, renamed, deleted (registry entry only), or expunged (registry entry + files).

The registry persists across sessions in =registry.eld= (stored under ~user-emacs-directory~ or ~no-littering-var-directory~ if available).

* Schema Files

Each database is paired with a =.schema.el= file that defines its structure.  This file is an ordinary Elisp file evaluated at database load time.

** Anatomy

#+begin_src emacs-lisp
(tabularium-define-schema "expenses"
  :file "~/Documents/expenses.db"
  :fields
  '((:id row_id :type integer :label "ID" :primary t :width 5)
    (:id date :type text :label "Date" :default today :width 12)
    (:id category :type choice :label "Category" :width 12
     :choice ("Food" "Transport" "Utilities" "Entertainment" "Other"))
    (:id amount :type number :label "Amount" :width 10)
    (:id description :type text :label "Description" :width 30
     :complete historical))
  :quick-entry-fields '(date category amount description)
  :default-sort 'asc
  :views
  '((:name "Recent"
     :filter (:field date :op ">=" :value "2024-01-01")
     :sort ((date . desc)))
    (:name "High Value"
     :filter (:field amount :op ">" :value "100")
     :columns (date category amount)
     :default t)))
#+end_src

** Field types

| Type     | Description                                            |
|----------+--------------------------------------------------------|
| ~text~     | Free-form text                                         |
| ~integer~  | Whole numbers (auto-increment if primary)              |
| ~number~   | Decimal numbers                                        |
| ~date~     | Date values (YYYY-MM-DD)                               |
| ~time~     | Time-of-day values (HH:MM or HH:MM:SS)                 |
| ~datetime~ | Timestamp values (YYYY-MM-DD HH:MM[:SS] or with `T')   |
| ~choice~   | Constrained selection from ~:choice~                     |
| ~boolean~  | Constrained yes/no pair                                |

** Field properties

| Property       | Type         | Description                                                                  |
|----------------+--------------+------------------------------------------------------------------------------|
| ~:id~            | symbol       | Field identifier (required)                                                  |
| ~:type~          | symbol       | One of the types listed above                                                |
| ~:label~         | string       | Display label                                                                |
| ~:primary~       | boolean      | Marks the row-ID field — exactly one field per schema (see below)            |
| ~:required~      | boolean      | Field cannot be left empty                                                   |
| ~:width~         | integer      | Column width in view mode                                                    |
| ~:default~       | any          | Default value (~today~, ~now~, a function, or a literal)                         |
| ~:choice~        | list         | Valid options for ~choice~ type                                                |
| ~:boolean-pair~  | list         | Canonical (true false) pair for ~boolean~ type                                 |
| ~:computed~      | string/plist | SQL expression or Elisp function                                             |
| ~:complete~      | symbol/plist | Completion source (see below)                                                |
| ~:long~          | boolean      | Open dedicated editing buffer for multi-paragraph text                       |
| ~:pattern~       | string       | Regex the entered value must match                                           |
| ~:pattern-help~  | string       | Error message shown on ~:pattern~ mismatch (otherwise generated)               |
| ~:validate~      | function     | =(lambda (value) ...)= returning nil if valid, or an error string            |

The ~:default~ value ~now~ is interpreted relative to the field type: ~time~ fields receive the current time per ~tabularium-time-format~; ~date~ fields receive today's date per ~tabularium-date-format~; ~datetime~ fields and any other type receive the current timestamp per ~tabularium-datetime-format~.

*Row ID.* Exactly one field per schema carries ~:primary t~ — it holds each row's *row ID*, the integer that uniquely identifies the row and that move, sort, mark, undo/redo, and export all use to refer to rows.  When the creation wizard or importer adds this field automatically it names it ~row_id~ with the label ~ID~; you may instead mark any field of your own ~:primary t~.  "Row ID" is the value/concept; "field id" or "column id" (the ~:id~ keyword every field carries) is a separate thing — every column has a ~:id~, but only the primary field's value is a row ID.

Storage of date / time / datetime values: SQLite columns are TEXT in ISO 8601 form (lexically sortable); PostgreSQL columns use the native DATE, TIME, and TIMESTAMP types respectively.  Datetime input accepts either a space (~2026-05-18 14:30:00~) or a T (~2026-05-18T14:30:00~) between the date and time portion; output is always emitted with a space.

Validation runs in this order on every prompted edit: type check → ~:pattern~ → ~:validate~.  The first failure short-circuits and the message is shown inline; the prompt re-loops with the rejected value as the initial input so the user can correct it.  Empty input always passes validation so a field can be cleared.  Pattern matching is always case-sensitive; write the regex's character classes accordingly (=[A-Za-z]+= rather than =[A-Z]+= when both cases should match).

** Completion sources

The ~:complete~ property configures intelligent completion during data entry.

| Type       | Syntax                                          | Description                                               |
|------------+-------------------------------------------------+-----------------------------------------------------------|
| ~historical~ | ~:complete historical~                            | Frequency-ranked past entries                             |
| ~recent~     | ~:complete recent~                                | Recency-ranked past entries                               |
| ~vocabulary~ | ~:complete (:type vocabulary :source "file.txt")~ | External file (one value per line) or inline ~:values~ list |
| ~related~    | ~:complete (:type related :field surgeon)~        | Values co-occurring with another field's current value    |
| ~filtered~   | ~:complete (:type filtered :where "active = 1")~  | Historical values filtered by ~SQL WHERE~                   |
| ~function~   | ~:complete (:type function :fn my-fn)~            | Custom Elisp function receiving field name and context    |
| ~union~      | ~:complete (:type union :sources (...))~          | Combine multiple sources; duplicates removed              |

All types accept an optional ~:limit N~ to cap the candidate count.  Related completion supports ~:autofill t~ to pre-fill with the most frequent co-occurring value.

A shorthand syntax is also available: ~(:complete (vocabulary "~/codes.txt"))~, ~(:complete (related columnX))~, etc.

** Saved views

Views are defined in the ~:views~ property of the schema as a list of plists.  Each view may specify ~:name~, ~:filter~ (with ~:field~, ~:op~, ~:value~), ~:sort~ (list of =(column . direction)= pairs), ~:columns~ (list of visible columns), and ~:default t~ (applied on open).

** Highlighting (conditional formatting)

Tabularium can highlight matching rows or cells in view mode.  There are two ways to set highlights up: interactively from the view buffer, and declaratively in the schema file.

*** Interactive highlighting

The ~h~ prefix in view mode applies highlight rules to the current table, additively — each new rule layers on top of the previous ones.  When several rules match the same cell their faces *stack*: the default face palette is grouped into three independent layers — a background color, a foreground color, and a style attribute — so a cell can carry one of each at once.  Each rule command prompts for the columns it should target.

| Key       | Command                               | Effect                                       |
|-----------+---------------------------------------+----------------------------------------------|
| ~h h~     | ~tabularium-view-highlight-rows~       | quick-highlight marked rows (or the row at point) |
| ~h \~     | ~tabularium-view-highlight-column~     | quick-highlight the column at point          |
| ~h |~     | ~tabularium-view-highlight-columns~    | quick-highlight chosen columns               |
| ~h a~     | ~tabularium-view-highlight-new~        | new rule — prompts for the rule type        |
| ~h n~     | ~tabularium-view-highlight-numeric~    | cells matching a comparison (~>~ ~<~ ~>=~ ~<=~ ~=~ ~!=~) |
| ~h d~     | ~tabularium-view-highlight-duplicates~ | cells whose value is duplicated in a column |
| ~h r~     | ~tabularium-view-highlight-regexp~     | cells whose text matches a regexp           |
| ~h l~     | ~tabularium-view-highlight-buffer~     | opens the Highlight Rules List buffer        |
| ~h x~     | ~tabularium-view-highlight-remove~     | removes rules (all, unsaved, or one)         |
| ~h X~     | ~tabularium-view-highlight-expunge~    | expunges saved rules from the schema         |
| ~h s~     | ~tabularium-view-highlight-save~       | saves one runtime rule into the schema file   |
| ~h S~     | ~tabularium-view-highlight-save-all~   | saves the whole view's highlight state        |

For quick on-the-fly work, three commands need only a face: ~h h~ tints the marked rows (or the row at point), ~h \~ tints the column under point, and ~h |~ tints columns chosen from the selector.  Each adds a real rule to the list, so it can be removed, reordered, modified, or saved like any other.  ~h a~ is the full dispatcher: it prompts for the rule type and runs the matching command.  The three typed rule commands (~h n~, ~h d~, ~h r~) each prompt for the target columns with a comma-separated ~completing-read-multiple~ selector — the ~<<ALL>>~ sentinel, or an empty answer, targets every visible column — and echo the chosen columns back in a ~[...]~ hint.  This is the same field-selection paradigm the filter and mark commands use: pick one column, several, or all.  Each command then prompts for a face, chosen from ~tabularium-highlight-faces~ — a customizable palette whose default entries are grouped ~bg:~, ~fg:~, and ~style:~, with the same ten WCAG-AAA hues offered for both color layers.

The ~h n~ numeric command offers only columns where a comparison is meaningful — integer, number, date, time, and datetime.  Because ISO date/time strings order chronologically as text, the same comparison expresses "later than" / "earlier than" for date, time, and datetime columns without a separate command.

All rules are numbered in evaluation order — saved rules first as the stable base, runtime rules layered on top — so the stacking hierarchy is visible.  ~h x~ removes rules: its prompt lists every rule — runtime and saved alike — and offers ~<<ALL>>~ (the default — remove every rule), ~<<UNSAVED>>~ (remove only the session's unsaved rules), and each individual rule.  Removing a saved rule only *hides* it in the current view — the schema is never mutated, so reopening the database brings every saved rule back.  ~h s~ persists one chosen runtime rule, ~h S~ persists the whole view state (runtime rules added, hidden rules dropped), and ~h X~ expunges every saved rule; these three are the only highlight commands that write the schema file.  Adding and removing rules is tracked by undo/redo.

~h l~ opens the *Highlight Rules List* buffer, an interactive list of every rule numbered in evaluation order with a "Saved?" column.  From it, ~a~ adds a new rule, ~m~/~u~/~U~/~t~ mark and unmark rules, ~x~ removes the marked rules (or the one at point), ~RET~ modifies a rule, ~M-p~/~M-n~ move a rule within its group, ~s~ saves the marked rules, ~S~ saves all, and ~X~ expunges — rule management in one place.  The buffer refreshes automatically as the rules change.

Rules added interactively live only in the current session until ~h s~ or ~h S~ writes them into the schema's ~:highlight~ property, the same way ~v s~ persists a saved view.

*** Declarative highlighting

The ~:highlight~ schema property holds a list of rule plists, applied to every view of the database.  Each rule is a plist with ~:scope~ ~row~ or ~cell~ and a ~:face~ to apply.  Every rule that matches contributes its face; the faces stack in evaluation order (runtime rules ahead of schema rules), so later faces win any conflicting attribute.

Row rules use ~:test~, a function receiving the row alist:

#+begin_src elisp
:highlight
'((:scope row
   :test (lambda (row) (equal (alist-get 'status row) "Overdue"))
   :face error))
#+end_src

Cell rules use ~:field~ to name the target column.  They can match with a ~:test~ function (receiving the cell value and row alist), a ~:value~ literal-equality shorthand, or a ~:builtin~ keyword naming one of the built-in rule types (~compare~, ~duplicates~, ~regex~, ~all~) — the same types the interactive ~h~ commands generate.  A row-scoped ~:builtin rows~ rule, carrying ~:row-ids~, matches a fixed set of rows by primary key — this is what the quick ~h h~ command produces:

#+begin_src elisp
:highlight
'((:scope cell :field status :value "Open"    :face success)
  (:scope cell :field status :value "Closed"  :face shadow)
  (:scope cell :field amount :builtin compare
   :op ">" :operand "10000" :face warning)
  (:scope cell :field tags :builtin duplicates :face tabularium-highlight-blue))
#+end_src

Cell rules can co-exist with row rules; cell faces are applied to the cell text, while row faces are applied via overlay.  Mark and freeze overlays sit on top of highlighting.

** Schema modification

Columns can be added, deleted, or edited interactively from view mode.  These operations update both the SQLite database and the schema file.  The schema file can also be edited directly and reloaded without restarting.

** Computed-field helpers

Fields defined with ~:computed~ derive their value from an SQL expression or an Elisp function evaluated against the row, conceptually similar to formulae in spreadsheet software.  Computed fields are not stored — they are evaluated on read.  An Elisp ~:computed~ expression receives the current row as an alist.  Helpers are grouped into four categories: conditional logic, same-row aggregation, date arithmetic, and cross-row lookup.

*** Conditional logic

| Helper                                             | Purpose                                                                        |
|----------------------------------------------------+--------------------------------------------------------------------------------|
| ~(tabularium-fn-if CONDITION THEN ELSE)~             | Inline conditional expression                                                  |
| ~(tabularium-fn-case VALUE T1 R1 T2 R2 ... DEFAULT)~ | Match VALUE against tests, return the paired result; optional trailing default |

*** Same-row aggregation

| Helper                                                  | Purpose                                                             |
|---------------------------------------------------------+---------------------------------------------------------------------|
| ~(tabularium-fn-sum-fields ROW FIELD1 FIELD2 ...)~        | Sum numeric values of named fields in ROW (non-numeric counts as 0) |
| ~(tabularium-fn-concat-fields ROW SEP FIELD1 FIELD2 ...)~ | Concatenate string values, skipping empty/missing fields            |

*** Date, time, and datetime arithmetic

The =fn-*= helpers below cover three logically distinct kinds of value: =date= (YYYY-MM-DD), =time= (HH:MM:SS, treated as a time of day), and =datetime= (a full timestamp).  Naming follows the type: =fn-date-*= for whole-day arithmetic, =fn-time-*= for time-of-day arithmetic (wraps modulo 24h), =fn-datetime-*= for cross-day-aware timestamp arithmetic.  All functions return nil on empty or unparseable input so chains stay safe.

| Helper                                              | Purpose                                                                              |
|-----------------------------------------------------+--------------------------------------------------------------------------------------|
| ~(tabularium-fn-today)~                               | Return today's date as ~YYYY-MM-DD~                                                    |
| ~(tabularium-fn-time-now)~                            | Return the current time as ~HH:MM:SS~                                                  |
| ~(tabularium-fn-datetime-now)~                        | Return the current timestamp as ~YYYY-MM-DD HH:MM:SS~                                  |
| ~(tabularium-fn-date-add DATE DAYS)~                  | Add DAYS to DATE; DAYS may be negative                                               |
| ~(tabularium-fn-date-diff DATE1 DATE2)~               | Days between DATE1 and DATE2 (DATE2 − DATE1)                                         |
| ~(tabularium-fn-time-add TIME SECONDS)~               | Add SECONDS to TIME; result wraps modulo 24h                                         |
| ~(tabularium-fn-time-diff START END)~                 | Seconds between two times-of-day (END − START); no day-wrap inference                |
| ~(tabularium-fn-datetime-add DATETIME SECONDS)~       | Add SECONDS to DATETIME, crossing day boundaries as needed                           |
| ~(tabularium-fn-datetime-diff START END)~             | Seconds between two datetimes (END − START); accepts T or space separators           |
| ~(tabularium-fn-datetime-date DATETIME)~              | Extract the ~YYYY-MM-DD~ portion of a datetime                                         |
| ~(tabularium-fn-datetime-time DATETIME)~              | Extract the ~HH:MM:SS~ portion of a datetime                                           |
| ~(tabularium-fn-datetime-combine DATE TIME)~          | Combine a date and a time into a datetime                                            |
| ~(tabularium-fn-duration-format SECONDS &optional STYLE)~ | Format a second-count as ~H:MM:SS~ (~colon~, default) or ~Hh Mm Ss~ (~units~); signed |
| ~(tabularium-fn-age DATE &optional REFERENCE)~        | Whole years between DATE and REFERENCE (defaults to today)                           |

*** Cross-row lookup and aggregation

| Helper                                                        | Purpose                                                    |
|---------------------------------------------------------------+------------------------------------------------------------|
| ~(tabularium-fn-lookup LOOKUP-FIELD LOOKUP-VALUE RETURN-FIELD)~ | First row's RETURN-FIELD where LOOKUP-FIELD = LOOKUP-VALUE |
| ~(tabularium-fn-count-where FIELD VALUE)~                       | Number of rows where FIELD = VALUE                         |
| ~(tabularium-fn-sum-where SUM-FIELD FILTER-FIELD VALUE)~        | Sum of SUM-FIELD across rows where FILTER-FIELD = VALUE    |

The cross-row helpers query the open database directly.  They are safe to call from inside ~:computed~ lambdas because computed fields are evaluated only when the database is active.  All values are escaped via ~tabularium-db-sql-quote~ before interpolation, so user-supplied strings cannot break the SQL.

* Extending Tabularium

External packages can inject content and behavior into Tabularium through a small plugin API exposed by ~tabularium-entry-mode~.

** Hooks

| Hook                                      | When it fires                                                                                                                                                                                                                                                                                                                                                                      |
|-------------------------------------------+------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| ~tabularium-entry-pre-render-hook~          | Inside `tabularium-entry-render', before the buffer is laid out.  Use this to set buffer-local variables that the layout pass consults                                                                                                                                                                                                                                             |
| ~tabularium-entry-render-hook~              | At the end of form buffer rendering, after the standard hint lines but before cursor positioning.  Use to inject content such as cross-table data or schema-specific hints                                                                                                                                                                                                         |
| ~tabularium-entry-new-hook~                 | After a new entry buffer is initialized (~tabularium-entry-editing-id~ is nil) and before the first render.  Use to populate plugin-specific defaults via ~tabularium-entry--values~                                                                                                                                                                                                   |
| ~tabularium-entry-pre-submit-hook~          | Just before the form is submitted, in both new and edit paths.  Use to update bookkeeping fields (e.g. a date-modified timestamp) before they are written to the database                                                                                                                                                                                                          |
| ~tabularium-entry-required-field-functions~ | List of predicates called with =(FIELD-NAME VALUES)= during render and submit.  Returning non-nil marks FIELD-NAME as dynamically required for the current entry's state — useful for type-specific required fields that cannot be expressed by a static `:required t'.  Marked fields display `+' (vs `*' for static `:required t'), and submission errors if such a field is empty |
| ~tabularium-entry-field-changed-functions~  | Abnormal hook called with =(FIELD-NAME OLD-VALUE NEW-VALUE)= after each interactive field change (edit, clear, default, autofill).  Plugins may further mutate ~tabularium-entry--values~ in response (e.g. clearing dependent fields, eagerly computing derived values).  Mutations from this hook will themselves fire the hook, so guard against unbounded recursion                |

** Header function

A header function returns a string to be inserted between the title bar and the field list — useful for rendering a citation, summary, or other contextual content.  Two ways to install one:

- *Schema-level*: set ~:header-function~ in the schema definition.  This is the cleanest path when the header applies to every entry of that schema.
- *Buffer-local*: set ~tabularium-entry-header-function~ to a function in a buffer.  When set, this overrides the schema-level value.

In either case the function takes no arguments and should return a string (with optional newlines) or nil for no header.

** Navigable text property

The ~tabularium-navigable~ text property identifies lines (in addition to schema-field overlays) that should participate in field-by-field navigation.  Plugin-injected lines carrying this property are visited by the same navigation commands that move between schema fields.

** Layout context

During and after the render, plugin code may read these buffer-local variables for context:

- ~tabularium-entry-schema-name~ — name of the schema for the current entry buffer (string)
- ~tabularium-entry-editing-id~ — ID of the entry being edited, or nil for a new (unsaved) entry
- ~tabularium-entry-first-field-line~ — line number of the first schema field in the form
- ~tabularium-entry-footer-start~ — buffer position where the footer hint lines begin

Plugins may also mutate ~tabularium-entry--values~ from within the new- and pre-submit-hooks to populate or update field values before render or save.

** Helper functions

- ~tabularium-entry-all-nav-positions~ returns a sorted list of navigable positions in the form, merging schema-field overlays and plugin-contributed navigable lines
- ~tabularium-entry-render~ re-renders the form buffer; plugins should call this after mutating data they have injected via the render hook
- ~tabularium-entry-edited-p~ returns non-nil if the form has unsaved changes

* Import and Export

** Import

The importer automatically detects header rows, infers data types, sanitizes column names, identifies likely primary keys, and adds historical completion for repeated text values.

There are two import modes.  ~tabularium-import~ always creates a *new* database from the file and registers it.  ~tabularium-import-append~ appends a file's rows to the database that is already open — columns are matched to schema fields by header name, trying field ids first and falling back to human-readable labels only if no id matches (matching is case-insensitive), and the primary-key column is never written, so the database assigns fresh IDs and appended rows cannot collide with existing ones.  In the menus and bare keymap the two live under an =i= prefix (=i i=, =i a=); =<= works as an alternative prefix (=< i=, =< a=).  Import precedes export in every menu.

| Command                              | Description                                      |
|--------------------------------------+--------------------------------------------------|
| ~tabularium-import~                    | Import a file as a new database (TSV/CSV/Org)    |
| ~tabularium-import-append~             | Append a file's rows to the open database        |
| ~tabularium-import-org-table-at-point~ | Import the org-table at point                    |
| ~tabularium-import-org-select-table~   | Select and import a named table from an org file |
| ~tabularium-import-org~                | Import an org-table into a specified database    |
| ~tabularium-import-csv~                | Import from a CSV file                           |
| ~tabularium-import-tsv~                | Import from a TSV file                           |
| ~tabularium-import-preview-schema~     | Preview the inferred schema before importing     |

** Export

| Command                     | Description                                              |
|-----------------------------+----------------------------------------------------------|
| ~tabularium-export~           | Export the marked rows, or the whole table if none marked |
| ~tabularium-export-all~       | Export the whole table, always — every non-computed column |
| ~tabularium-export-visible~   | Export the on-screen view — visible columns, filtered/sorted rows, view limit |
| ~tabularium-export-range~     | Export an explicit selection of row IDs and columns       |

All four prompt for TSV or CSV.  In the menus and the bare keymap they live under an =e= prefix (=e e=, =e a=, =e v=, =e r=); =>= works as an alternative prefix (=> e=, => a=, => v=, => r=).

TSV is recommended for version control, as it avoids the quoting ambiguities inherent to CSV with embedded commas.

* Technical Details

** File structure

| File                        | Description                                                  |
|-----------------------------+--------------------------------------------------------------|
| ~tabularium.el~               | Core: view mode, entry mode, registry, import/export, wizard |
| ~tabularium-db.el~            | Database backend interface (EIEIO)                           |
| ~tabularium-db-postgresql.el~ | PostgreSQL backend (optional, experimental)                  |
| ~tabularium-menu.el~          | Hydra and Transient menu definitions                         |
| ~tabularium-modeline.el~      | Mode-line integration                                        |

** Requirements

- Emacs 29.1+ (built-in SQLite support via ~sqlite.el~)
- SQLite 3.31+
- Optional: ~hydra~, ~transient~ (for menu interface)

** Syncing (Git, Syncthing, Dropbox)

Database and schema files are designed to travel together.  Before syncing or suspending, ~tabularium-sync-prepare~ checkpoints and closes all connections to ensure a clean state.  ~tabularium-sync-checkpoint~ flushes the write-ahead log without disconnecting.  ~tabularium-sync-cleanup-wal-files~ removes any orphaned =-wal= and =-shm= files left by interrupted sessions; it is safe to run when the database is closed.  ~tabularium-sync-fix-paths~ converts any absolute home directory paths in schema files to =~/= notation, ensuring portability across machines with different home directories.

TSV export provides human-readable diffs suitable for version control.

** Debugging

~tabularium-completion-debug~ inspects the completion configuration and current candidates for any field.  ~tabularium-undo-history~ displays the recorded undo and redo stacks for the current database.  ~tabularium-completion-clear-cache~ forces a reload of vocabulary files on the next completion request.  Setting ~tabularium-debug~ to a non-nil value enables verbose diagnostic messages during completion and autofill operations.
