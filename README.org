#+AUTHOR: Paul H. McClelland

*Structured data management in Emacs using SQL*

~tabularium~ provides a scalable data entry and management system within Emacs, using SQLite as its primary backend.  It is designed for datasets with thousands of entries and dozens of columns, in which standard Emacs tools begin to exhibit performance limitations.

* Design and Scope

~tabularium~ uses several built-in tools to create a data management ecosystem within Emacs, including ~tabulated-list-mode~ for row/column display and ~sqlite.el~ for the database backend.  The result is something close in spirit to Microsoft Access or LibreOffice Base, but fully integrated into Emacs—leveraging Emacs's standard completion frameworks, keyboard-driven navigation, and version control support.  Each database can also be extended with custom Elisp in its corresponding schema file, and several useful elements from common spreadsheet software such as Microsoft Excel and LibreOffice Calc are also implemented for ease-of-use.  An EIEIO-based backend abstraction layer supports future extensions to PostgreSQL and other database systems.

This package was developed out of a need to more adeptly handle large datasets within Emacs.  Emacs's built-in tools such as ~org-table~ and ~csv-mode~ handle human-readable tables and flat files well, but neither scales gracefully to thousands of records with rich schemas, field-level completion, or computed fields.  Conversely, packages like ~emacsql~ provide raw database access but lack a data management interface, and ~esqlite~ offers SQLite bindings without a user-facing layer.  ~tabularium~ is designed to occupy the space between these tools and full external database applications.

* Features

- *SQL-backed storage* — SQLite by default, with an extensible backend architecture
- *Schema-driven data structure* — field types, defaults, choices, validation, and computed fields
- *Multiple entry modes* — form-based (with per-field completion), minibuffer prompts, and quick entry for high-volume workflows
- *Rich querying* — filter, search, count, and aggregate across any field type; fuzzy find via ~completing-read~
- *Spreadsheet operations* — undo/redo, copy/paste, dired-style marking, multi-column sort, freeze rows, fill, query-replace, column clipboard, and reindexing
- *Completion system* — historical (frequency-ranked), recent, vocabulary (file or inline), related (contextual co-occurrence), filtered (~SQL WHERE~), custom function, and union sources
- *Saved views* — named presets for filter, sort, and column configuration
- *Import/export* — CSV, TSV, and org-table import; CSV/TSV export (RFC 4180-compliant)
- *Hydra and Transient menus* — discoverable command interface
- *Version control-friendly* — designed for Git and Syncthing workflows

Default keybindings for all modes are documented in [[file:KEYBINDINGS.org][KEYBINDINGS.org]].

* Installation

~tabularium~ is not yet available in any Emacs package repository.

** With ~elpaca~ or ~straight~

Install directly from the online repository using ~elpaca~ or ~straight~:

#+begin_src emacs-lisp
(use-package tabularium
  :ensure (:host codeberg :repo "phmcc/tabularium")
  :config
  (require 'tabularium-menu))
#+end_src

** Manual

Alternatively, clone the repository and put the package in the Emacs load path:

#+begin_src emacs-lisp
(add-to-list 'load-path "~/path/to/tabularium")
(require 'tabularium)
(require 'tabularium-menu)
#+end_src

* Quick Start

** 1. Create a database

#+begin_example
M-x tabularium-create-database RET expenses RET ~/Documents/expenses.db RET
#+end_example

This creates two paired files: =expenses.db= (the SQLite database) and =expenses.schema.el= (the schema definition).  An interactive wizard prompts for field definitions.

** 2. Edit the schema (optional)

The wizard produces a working schema, but the generated =.schema.el= file can be refined further—for instance, to add completion sources, views, or quick-entry fields.  See "Schema Files" below for the full specification.

** 3. Open and use

#+begin_example
M-x tabularium-open RET expenses RET
M-x tabularium-view RET
#+end_example

From the view buffer, entries can be created, edited, sorted, filtered, marked, and exported.  Form-based entry provides per-field completion; quick entry prompts only for selected fields.

* Entry Mode (~tabularium-entry-mode~)

Entry mode provides a form-based interface for creating and editing individual records.  Each field is displayed on its own line with its prompt label, and completion is available where configured in the schema.

Three entry methods are available:

- *Form entry* — opens a dedicated buffer with all fields laid out vertically; best for complex schemas and careful data entry.
- *Prompt entry* — prompts for each field sequentially in the minibuffer; suitable for quick keyboard-driven entry.
- *Quick entry* — prompts only for fields listed in ~:quick-entry-fields~; ideal for high-volume entry with consistent defaults.

The ~tabularium-entry-method~ variable controls the default method; a prefix argument before any entry command invokes the alternative.

* Registry Mode (~tabularium-registry-mode~)

The registry tracks all known databases.  ~M-x tabularium-registry~ displays a listing with each database's name, schema status, and file path.  From this buffer, databases can be opened, viewed, created, registered, renamed, deleted (registry entry only), or expunged (registry entry + files).

The registry persists across sessions in =registry.eld= (stored under ~user-emacs-directory~ or ~no-littering-var-directory~ if available).

* Schema Files

Each database is paired with a =.schema.el= file that defines its structure.  This file is an ordinary Elisp file evaluated at database load time.

** Anatomy

#+begin_src emacs-lisp
(tabularium-define-schema "expenses"
  :file "~/Documents/expenses.db"
  :fields
  '((:name id :type integer :prompt "ID" :primary t :width 5)
    (:name date :type text :prompt "Date" :default today :width 12)
    (:name category :type choice :prompt "Category" :width 12
     :choice ("Food" "Transport" "Utilities" "Entertainment" "Other"))
    (:name amount :type number :prompt "Amount" :width 10)
    (:name description :type text :prompt "Description" :width 30
     :complete historical))
  :quick-entry-fields '(date category amount description)
  :default-sort 'asc
  :views
  '((:name "Recent"
     :filter (:field date :op ">=" :value "2024-01-01")
     :sort ((date . desc)))
    (:name "High Value"
     :filter (:field amount :op ">" :value "100")
     :columns (date category amount)
     :default t)))
#+end_src

** Field types

| Type    | Description                               |
|---------+-------------------------------------------|
| ~text~    | Free-form text                            |
| ~integer~ | Whole numbers (auto-increment if primary) |
| ~number~  | Decimal numbers                           |
| ~date~    | Date values (YYYY-MM-DD)                  |
| ~choice~  | Constrained selection from ~:choice~       |

** Field properties

| Property  | Type         | Description                                            |
|-----------+--------------+--------------------------------------------------------|
| ~:name~     | symbol       | Field identifier (required)                            |
| ~:type~     | symbol       | One of the types listed above                          |
| ~:prompt~   | string       | Display label                                          |
| ~:primary~  | boolean      | Primary key field                                      |
| ~:width~    | integer      | Column width in view mode                              |
| ~:default~  | any          | Default value (~today~, ~now~, a function, or a literal)   |
| ~:choice~  | list         | Valid options for ~choice~ type                          |
| ~:computed~ | string/plist | SQL expression or Elisp function                       |
| ~:complete~ | symbol/plist | Completion source (see below)                          |
| ~:long~     | boolean      | Open dedicated editing buffer for multi-paragraph text |

** Completion sources

The ~:complete~ property configures intelligent completion during data entry.

| Type       | Syntax                                          | Description                                               |
|------------+-------------------------------------------------+-----------------------------------------------------------|
| ~historical~ | ~:complete historical~                            | Frequency-ranked past entries                             |
| ~recent~     | ~:complete recent~                                | Recency-ranked past entries                               |
| ~vocabulary~ | ~:complete (:type vocabulary :source "file.txt")~ | External file (one value per line) or inline ~:values~ list |
| ~related~    | ~:complete (:type related :field surgeon)~        | Values co-occurring with another field's current value    |
| ~filtered~   | ~:complete (:type filtered :where "active = 1")~  | Historical values filtered by ~SQL WHERE~                   |
| ~function~   | ~:complete (:type function :fn my-fn)~            | Custom Elisp function receiving field name and context    |
| ~union~      | ~:complete (:type union :sources (...))~          | Combine multiple sources; duplicates removed              |

All types accept an optional ~:limit N~ to cap the candidate count.  Related completion supports ~:autofill t~ to pre-fill with the most frequent co-occurring value.

A shorthand syntax is also available: ~(:complete (vocabulary "~/codes.txt"))~, ~(:complete (related columnX))~, etc.

** Saved views

Views are defined in the ~:views~ property of the schema as a list of plists.  Each view may specify ~:name~, ~:filter~ (with ~:field~, ~:op~, ~:value~), ~:sort~ (list of =(column . direction)= pairs), ~:columns~ (list of visible columns), and ~:default t~ (applied on open).

** Schema modification

Columns can be added, deleted, or edited interactively from view mode.  These operations update both the SQLite database and the schema file.  The schema file can also be edited directly and reloaded without restarting.

** Computed-field helpers

Fields defined with ~:computed~ derive their value from an SQL expression or an Elisp function evaluated against the row, conceptually similar to formulae in spreadsheet software.  Computed fields are not stored — they are evaluated on read.  An Elisp ~:computed~ expression receives the current row as an alist.  Helpers are grouped into four categories: conditional logic, same-row aggregation, date arithmetic, and cross-row lookup.

*** Conditional logic

| Helper                                              | Purpose                                                             |
|-----------------------------------------------------+---------------------------------------------------------------------|
| ~(tabularium-fn-if CONDITION THEN ELSE)~                 | Inline conditional expression                                       |
| ~(tabularium-fn-case VALUE T1 R1 T2 R2 ... DEFAULT)~     | Match VALUE against tests, return the paired result; optional trailing default |

*** Same-row aggregation

| Helper                                              | Purpose                                                             |
|-----------------------------------------------------+---------------------------------------------------------------------|
| ~(tabularium-fn-sum-fields ROW FIELD1 FIELD2 ...)~       | Sum numeric values of named fields in ROW (non-numeric counts as 0) |
| ~(tabularium-fn-concat-fields ROW SEP FIELD1 FIELD2 ...)~ | Concatenate string values, skipping empty/missing fields           |

*** Date arithmetic

| Helper                                              | Purpose                                                             |
|-----------------------------------------------------+---------------------------------------------------------------------|
| ~(tabularium-fn-today)~                                  | Return today's date as ~YYYY-MM-DD~                                   |
| ~(tabularium-fn-now)~                                    | Return the current timestamp as ISO 8601                            |
| ~(tabularium-fn-date-add DATE DAYS)~                     | Add DAYS to DATE; DAYS may be negative                              |
| ~(tabularium-fn-date-diff DATE1 DATE2)~                  | Days between DATE1 and DATE2 (DATE2 − DATE1)                        |
| ~(tabularium-fn-age DATE &optional REFERENCE)~           | Whole years between DATE and REFERENCE (defaults to today)          |

*** Cross-row lookup and aggregation

| Helper                                              | Purpose                                                             |
|-----------------------------------------------------+---------------------------------------------------------------------|
| ~(tabularium-fn-lookup LOOKUP-FIELD LOOKUP-VALUE RETURN-FIELD)~ | First row's RETURN-FIELD where LOOKUP-FIELD = LOOKUP-VALUE       |
| ~(tabularium-fn-count-where FIELD VALUE)~                | Number of rows where FIELD = VALUE                                  |
| ~(tabularium-fn-sum-where SUM-FIELD FILTER-FIELD VALUE)~ | Sum of SUM-FIELD across rows where FILTER-FIELD = VALUE             |

The cross-row helpers query the open database directly.  They are safe to call from inside ~:computed~ lambdas because computed fields are evaluated only when the database is active.  All values are escaped via ~tabularium-db-sql-quote~ before interpolation, so user-supplied strings cannot break the SQL.

* Extending Tabularium

External packages can inject content and behavior into Tabularium through a small plugin API exposed by ~tabularium-entry-mode~.

** Hooks

| Hook                              | When it fires                                                                                         |
|-----------------------------------+-------------------------------------------------------------------------------------------------------|
| ~tabularium-entry-pre-render-hook~  | Inside `tabularium-entry-render', before the buffer is laid out.  Use this to set buffer-local variables (notably ~tabularium-entry-header-function~) that the layout pass consults |
| ~tabularium-entry-render-hook~      | At the end of form buffer rendering, after the standard hint lines but before cursor positioning.  Use to inject content such as cross-table data or schema-specific hints           |
| ~tabularium-entry-new-hook~         | After a new entry buffer is initialized (~tabularium-entry-editing-id~ is nil) and before the first render.  Use to populate plugin-specific defaults via ~tabularium-entry--values~  |
| ~tabularium-entry-pre-submit-hook~  | Just before the form is submitted, in both new and edit paths.  Use to update bookkeeping fields (e.g. a date-modified timestamp) before they are written to the database          |
| ~tabularium-entry-required-field-functions~ | List of predicates called with =(FIELD-NAME VALUES)= during render and submit.  Returning non-nil marks FIELD-NAME as dynamically required for the current entry's state — useful for type-specific required fields that cannot be expressed by a static `:required t'.  Marked fields display `+' (vs `*' for static `:required t'), and submission errors if such a field is empty |

** Header function

The buffer-local variable ~tabularium-entry-header-function~, when non-nil, is called with no arguments during render and should return a string to be inserted between the title bar and the field list.  Plugins use this to render a citation, summary, or other contextual content.  Set it from ~tabularium-entry-pre-render-hook~ for it to take effect on first render.

** Navigable text property

The ~tabularium-navigable~ text property identifies lines (in addition to schema-field overlays) that should participate in field-by-field navigation.  Plugin-injected lines carrying this property are visited by the same navigation commands that move between schema fields.

** Layout context

During and after the render, plugin code may read these buffer-local variables for context:

- ~tabularium-entry-schema-name~ — name of the schema for the current entry buffer (string)
- ~tabularium-entry-editing-id~ — ID of the entry being edited, or nil for a new (unsaved) entry
- ~tabularium-entry-first-field-line~ — line number of the first schema field in the form
- ~tabularium-entry-footer-start~ — buffer position where the footer hint lines begin

Plugins may also mutate ~tabularium-entry--values~ from within the new- and pre-submit-hooks to populate or update field values before render or save.

** Helper functions

- ~tabularium-entry-all-nav-positions~ returns a sorted list of navigable positions in the form, merging schema-field overlays and plugin-contributed navigable lines
- ~tabularium-entry-render~ re-renders the form buffer; plugins should call this after mutating data they have injected via the render hook
- ~tabularium-entry-edited-p~ returns non-nil if the form has unsaved changes

TSV is recommended for version control, as it avoids the quoting ambiguities inherent to CSV with embedded commas.

** Syncing (Git, Syncthing, Dropbox)

Database and schema files are designed to travel together.  Before syncing or suspending, ~tabularium-sync-prepare~ checkpoints and closes all connections to ensure a clean state.  ~tabularium-sync-checkpoint~ flushes the write-ahead log without disconnecting.  ~tabularium-sync-cleanup-wal-files~ removes any orphaned =-wal= and =-shm= files left by interrupted sessions; it is safe to run when the database is closed.  ~tabularium-sync-fix-paths~ converts any absolute home directory paths in schema files to =~/= notation, ensuring portability across machines with different home directories.

TSV export provides human-readable diffs suitable for version control.

** Debugging

~tabularium-completion-debug~ inspects the completion configuration and current candidates for any field.  ~tabularium-undo-history~ displays the recorded undo and redo stacks for the current database.  ~tabularium-completion-clear-cache~ forces a reload of vocabulary files on the next completion request.  Setting ~tabularium-debug~ to a non-nil value enables verbose diagnostic messages during completion and autofill operations.
