* Roadmap

The following features are tentatively planned for future releases:

** v0.5.0

- [X] Conditional Formatting
  - [X] Row highlighting based on field values
  - [X] Color-coded status indicators

- [X] Field Validation
  - [X] Reject invalid data on entry
  - [X] Custom validation functions
  - [X] Regex patterns for text fields

- [X] ~time~ and ~datetime~ field types
  - [X] ~time~ stored as ISO 8601 HH:MM[:SS]
  - [X] ~datetime~ stored as ISO 8601 YYYY-MM-DD HH:MM[:SS] (accepts T or space separator)
  - [X] Validation and default-to-now option
  - [X] Date/time/datetime arithmetic helpers (=fn-time-add=, =fn-datetime-diff=, =fn-duration-format=, etc.)

- [X] Quick-startup wizard
  - [X] One-shot prompt for all fields at once (e.g., =name:text:required age:integer date:date=)
  - [X] Schema generation from a pasted header row

- [X] Generate database from existing schema file
  - [X] Build the =.db= file by reading a hand-written or imported =.schema.el=
  - [X] Useful when the schema is moved between machines or restored from version control

- [X] Face customization via ~defface~ / ~defcustom~
  - [X] Tabulated-list header face
  - [X] Marked-row face
  - [X] Frozen-row face
  - [X] Sort-indicator face
  - [X] Filter / view-status face in the modeline
  - [X] Group all under a ~tabularium-faces~ customize group

** v0.5.3

- [X] Pre-release hardening pass
  - [X] Extend the ERT suite to cover pure helpers (statistics, escaping, SQL clause construction, schema accessors, undo/redo and kill-ring mechanics)
  - [X] Keymap audit test: every command bound in a mode map still exists, so a file split cannot silently orphan a binding
  - [X] Escape =%= and =_= in substring searches so they match literally
  - [X] Accept a dotted =:boolean-pair= from a hand-edited schema file
  - [X] Naming, docstring, message, and header consistency pass
- [ ] Full manual run-through (see =MANUAL-TESTING.org=)

** v0.5.4 — computed-column formulas

- [X] ~tabularium-compute~ macro: one way to write a computed column, replacing the choice between a SQL expression string and an Emacs Lisp lambda
  - [X] Formulas are ordinary Lisp forms, so ~read~ is the parser; a head symbol names an operator, any other bare symbol is a column
  - [X] Dual backend: compiles to SQL when every operator has a SQL form, falls back to the existing post-fetch path otherwise
  - [X] SQL is the specification — the Lisp side is written to match SQLite where they would differ (rounding, modulo sign, 1-indexed substrings, null propagation)
  - [X] Polymorphic ~=~, so ~(= status "open")~ reads the way it looks
  - [X] Errors at macro expansion rather than blank cells at render
- [ ] Wire the formula prompt into ~| N~ and ~| E~, with completion over the operator table
- [ ] Decide whether ~sum-where~, ~count-where~, and ~lookup~ belong in the language (currently excluded; raw lambdas remain available)
- [ ] Document the operator table in the README, and the post-fetch seam in ~?~ describe

** v0.6.0 — first public release

- [ ] Modularization
  - [ ] Split ~tabularium.el~ into a flat ~lisp/~ directory, Magit-style: 17 essential modules plus 3 opt-in (~tabularium-menu~, ~tabularium-modeline~, ~tabularium-postgresql~)
  - [ ] Bottom-up extraction, byte-compiling and running the ERT suite after each module
  - [ ] Modularization only — no behavior changes bundled in
- [ ] Release preparation
  - [ ] Resolve the remaining ELPA compliance items (see =AUDIT.org=)
  - [ ] Submit to NonGNU ELPA, then MELPA
