* Roadmap

The following features are tentatively planned for future releases:

** v0.6.0

- [X] =:table= schema property, with ~tabularium-table-name~ as the fallback
- [X] Connections keyed by file and refcounted; =PRAGMA foreign_keys= at connect
- [X] Read-only relations: a schema may name a view
- [X] Registry lists one database per file, with its own display name
- [X] =:fk= with =REFERENCES= emission and delete policies
- [X] Entry-time validation and completion from live parent keys
- [X] Cascade snapshotting, so undo restores children
- [X] =t= table prefix: switch, step, list, reorder, follow a key
- [X] =l= / =L= master–detail with a locked filter
- [X] =(parent ...)=, =(children ...)=, =(lookup-in ...)= in formulas
- [X] =t ?= link integrity, =t == ghost tables
- [X] =i= dispatcher and associated import function variants
- [X] =e= dispatcher and associated import function variants
- [X] One ladder for a missing database and a missing schema
- [X] Org-capture-style schema drafting

** v0.6.1

- [ ] A join is declared as a *view-like schema*: several tables, the columns to take from each, and the links to join on.  Reusing the read-only machinery means sorting, filtering, highlighting, and aggregating work on it the day it exists
- [ ] Export a join to CSV/TSV/Org, which is the case a join is usually wanted for
- [ ] Inner and left joins; the rest can wait for a case that needs them

** v0.6.2

- [ ] *Schema migration.* Adding a =:fk= to an existing table does nothing: SQLite adds constraints only at =CREATE TABLE=.  Today the only cure is to delete the database and rebuild, which makes the whole link feature usable on new databases only.  ~tabularium--rebuild-table-dropping~ already does the copy-and-swap dance for column deletion; generalizing it to "rebuild this table from its current schema" closes the gap and makes every constraint below retroactive
- [ ] *=NOT NULL= and =UNIQUE= in the DDL.*  =:required= is checked at entry and =:unique= does not exist; neither reaches the database, so anything writing to the file another way can break what the schema promises
- [ ] *=:on-update=.*  The delete policies are there; changing a parent key silently orphans its children
- [ ] *Composite keys.*  =:pk t= marks one field, and =:fk= names one column.  A key of (patient_id, visit_date) cannot be expressed, which rules out a large class of real data.  Touches the storage layer, so cheaper before modularization than after

** v0.6.3

- [ ] =t ?= reports orphans; nothing fixes them.  Reassign, null out, or delete, on the rows it found
- [ ] Rebuild a table from its schema (the migration command above, exposed)

** v0.7.0

- [ ] Modularization into smaller files for easier maintenance
