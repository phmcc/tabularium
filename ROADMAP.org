* Roadmap

The following features are tentatively planned for future releases:

** v0.6.0

- [X] =:table= schema property, with ~tabularium-table-name~ as the fallback
- [X] Connections keyed by file and refcounted; =PRAGMA foreign_keys= at connect
- [X] Read-only relations: a schema may name a view
- [X] Registry lists one database per file, with its own display name
- [X] =:fk= with =REFERENCES= emission and delete policies
- [X] Entry-time validation and completion from live parent keys
- [X] Cascade snapshotting, so undo restores children
- [X] =t= table prefix: switch, step, list, reorder, follow a key
- [X] =l= / =L= master–detail with a locked filter
- [X] =(parent ...)=, =(children ...)=, =(lookup-in ...)= in formulas
- [X] =t ?= link integrity, =t == ghost tables
- [X] =i= dispatcher and associated import function variants
- [X] =e= dispatcher and associated import function variants
- [X] One ladder for a missing database and a missing schema
- [X] Org-capture-style schema drafting

** v0.6.1

- [X] Joining
  - Defined as a view-like schema
  - Several tables, the columns to take from each, and the links to join on.  Reusing the read-only machinery means sorting, filtering, highlighting, and aggregating work automatically
- [X] Export joins
  - CSV/TSV/Org formats
- [X] Inner and left joins (priority)

** v0.6.2

- [X] Schema migration
  - Adding a =:fk= to an existing table does nothing: SQLite adds constraints only at =CREATE TABLE=
  - Currently can only delete the database and rebuild, which makes the whole link feature usable on new databases only
  - ~tabularium--rebuild-table-dropping~ already does the copy-and-swap dance for column deletion; generalizing it to "rebuild this table from its current schema" closes the gap and makes every constraint below retroactive
- [X] =NOT NULL= and =UNIQUE= in the DDL
  - =:required= is checked at entry and =:unique= does not exist; neither reaches the database, so anything writing to the file another way can break what the schema promises
- [X] =:on-update=
  - The delete policies are there; changing a parent key silently orphans its children
- [X] Composite keys
  - =:pk t= marks one field, and =:fk= names one column.  A key of (patient_id, visit_date) cannot be expressed, which rules out a large class of real data
- [X] =t ?= reports orphans; nothing fixes them.  Reassign, null out, or delete, on the rows it found
- [X] Rebuild a table from its schema (the migration command above, exposed)
- [X] Add a custom background face for the primary key, as well as user-toggleable zebra striping

** v0.6.3

- [X] Aggregate a child column in a formula: =(children TABLE :sum COLUMN)=, with =:min= and =:max=
- [X] A row added in a detail view starts with its link to the parent filled in
- [X] Detail views follow a link over several columns, on every column of it

** v0.7.0

- [X] Pivot Tables
  - Defined as a view-like schema
- [X] Aggregate summaries
- [X] Cross-tabulation
- [X] Dynamic grouping
